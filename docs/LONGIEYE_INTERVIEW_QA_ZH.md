# LongiEye 项目面试深挖问答手册

> 基于 LongiEye v0.5.0 整理
> 适用方向：AI 工程师、机器学习工程师、医疗 AI 工程岗位
> 更新日期：2026-09-01

## 使用方法

回答 LongiEye 问题时，始终区分三个层次：

1. **工程链路正确**：数据合同、模型加载、错误边界、回退和部署流程能够按设计工作。
2. **数值行为兼容**：指定模型、预处理和运行时能够复现经过批准的输出。
3. **真实临床有效**：模型在真实人群中具有可验证的区分度、校准度、泛化能力和临床价值。

LongiEye 当前重点证明前两项，不能声称已经证明第三项。面试中主动说明边界，比夸大项目更能体现工程判断力。

## 一、数据与特征设计

### 1. 为什么采用“静态性别编码 + 8 项纵向变化量”这 9 维特征？

**推荐回答：**

当前特征不是经过真实数据实验验证后的最优方案，而是一个刻意简化、容易审计的纵向特征合同。Y1 和 Y2 固定间隔 12 个月，因此使用 `Y2 - Y1` 可以直接表达一年内变化的方向和幅度；性别在合同中被定义为静态变量，所以只保留一份。这样可以把两次高度相关的测量压缩成固定的 9 维输入，便于检查特征顺序、归一化参数和模型系数。

它的代价是表达能力下降。例如 140 cm 到 145 cm 和 170 cm 到 175 cm 都会被表示成 `+5`，模型看不到基线差异；佩镜状态 0 到 0 和 1 到 1 的变化量也都是 0。它还不能表达基线阈值、基线与变化量的交互，以及两个以上时间点的非线性轨迹。当前又使用线性逻辑回归，这种限制会更加明显。

进入真实研究后，我不会默认变化量方案最好，而会比较：

- `delta-only`
- `Y1 + delta`
- `Y1 + Y2`
- 必要时使用纵向或时序模型

最后通过参与者级验证、校准和外部验证决定特征方案。

**边界提醒：** 不要说“变化量已经证明比原始值更好”，因为当前仓库没有这项消融实验。

### 2. Y1/Y2 中某项测量缺失时怎么处理？

**推荐回答：**

当前版本不插值、不填默认值，而是拒绝推理。所有 Y1/Y2 测量字段都是严格必填字段。缺失字段会在进入领域对象和模型前被请求校验层拦截，HTTP 返回 `422`，错误码为 `request_validation_error`，指出缺失字段的位置，但不回显用户提交值。越界数值、Y1/Y2 性别不一致、随访间隔不是 12 个月，也会被继续拒绝。

这样做不是因为拒绝永远优于插值，而是项目没有真实训练分布，无法证明均值、中位数或其他插补策略合理。随意插补可能制造训练与推理之间的偏差。

真实项目中需要先研究缺失机制，并且只能在训练折中拟合插补参数，同时评估：

- 缺失指示变量是否有帮助
- 多重插补或支持缺失值的模型是否更合适
- 缺失率是否随医院、设备、时间和亚组漂移
- 在线缺失策略是否与训练和验证阶段完全一致

**边界提醒：** 当前不是“智能处理缺失值”，而是显式拒绝不完整输入。

### 3. OD/OS 双眼预测是独立建模还是联合建模？

**推荐回答：**

准确说法是：**独立目标头，但共享双眼输入**。

OD 和 OS 分别有一套逻辑回归系数和截距，损失独立计算，没有显式的联合概率、残差相关性或左右一致性约束。但两个头都会读取完整的 9 维输入，其中同时包含 OD 和 OS 的眼轴变化。合成标签规则里，本眼项权重较大，对侧眼也有较小交叉项。

所以当前实现利用了输入层面的双眼信息，但没有建模输出层面的联合分布。

真实研究中，我会首先按参与者而不是按眼拆分数据，避免同一个人的左右眼跨训练集和验证集；然后比较独立双头、共享主干多任务模型以及显式双眼交互模型，再通过外部验证判断复杂度是否真正带来收益。

**边界提醒：** 不要说“两眼完全独立”，也不要说“已经实现完整的联合概率模型”。

## 二、模型接入门禁

### 4. fail-closed 具体是怎么实现的？

**推荐回答：**

我把 fail-closed 放在研究模型的构造边界，而不是等到推理后再补救。研究模型必须连续通过以下步骤：

1. 严格解析 manifest，校验架构、9 维特征顺序、OD/OS 输出顺序、CPU、float32 等合同。
2. 验证包外审批回执，而不是相信模型包自己声明“已批准”。
3. 检查模型包只能包含规定的三个普通文件，拒绝符号链接、额外文件和超限文件。
4. 校验模型卡完整性及其 SHA-256。
5. 读取 checkpoint，并校验实际字节的 SHA-256。
6. 使用同一份已验证字节执行 `torch.load(weights_only=True)`。
7. 检查 state dict 的 key、shape、dtype 和有限数值。
8. 运行黄金向量自检。
9. 只有全部成功才进入 `ready`。

任何一步失败都不会静默切换到另一个模型。加载成功后也不是永久信任：预测时会检查审批回执有效期和内存中参数完整性，`readiness()` 还会重新读取外部回执，以发现撤销或替换。

**完整失败案例：**

假设已经批准的 `research_model.pt` 被替换，但 manifest 和外部回执没有变化。加载器计算实际 checkpoint 的 SHA-256 后发现不一致，立即抛出：

- 错误码：`artifact_digest_mismatch`
- 安全文案：`研究模型工件完整性校验失败。`

此时还没有调用 `torch.load`，adapter 不会创建，也不会回退到 demo 模型。

如果攻击者同时修改 manifest 中的哈希，但无法修改包外审批回执，那么整个审批请求摘要会改变，系统会更早返回 `approval_invalid`。

**边界提醒：** 研究 adapter 当前是离线路径，没有接入公开 FastAPI，因此这里返回的是 Python 边界异常，不应虚构 HTTP 状态码。

### 5. SHA-256 完整性校验防的是什么威胁？

**推荐回答：**

SHA-256 提供的是字节级完整性证据：证明当前读取的 checkpoint、模型卡和配置与审批时审查的内容完全一致。它可以发现传输损坏、误覆盖，以及只能修改模型包、不能修改可信审批记录的替换行为。

但哈希本身不提供真实性。如果攻击者既能替换模型，又能控制外部审批回执或 `ApprovalPolicy`，当前信任根就已经被攻破。此时再增加一次普通哈希没有意义，需要：

- 数字签名和受管密钥
- 有身份认证的审批服务
- 权限隔离与职责分离
- 不可篡改的审计记录
- 受保护的模型注册表

SHA-256 不能证明模型由谁训练、来源是否可信、是否含恶意内容、是否获得发布授权，也不能证明临床有效性。

另外，`weights_only=True`、文件大小限制以及 shape/dtype 检查只能缩小反序列化攻击面，不是完整的安全沙箱，也不能消除所有拒绝服务风险。

### 6. 黄金向量自检是怎么设计的？

**推荐回答：**

黄金向量是一组固定输入、预期 OD/OS 输出以及预先声明的数值容差。它不是训练样本，也不是模型性能测试，目标是检查：

> 获批模型 + 获批预处理 + 当前运行时，是否仍然保持预期的数值行为。

当前门禁要求至少三个不同案例，不能全部是零输入；必须包含左右不对称输入；OD 和 OS 输出不能始终相同；两个输出头都必须在案例之间发生变化。

每个案例会运行两次：

1. 检查重复推理是否确定。
2. 检查 OD/OS 是否落在预设容差内。

当前公开仓库没有真实研究模型或真实黄金向量。CI 使用完全合成的输入，预期输出由 demo 模型计算后冻结，只证明 adapter 工程合同。未来真实模型的黄金向量应在受控环境中由可信源运行时生成，并与模型版本一起审批和冻结。

黄金向量不是按周或按月更新，而是随模型版本事件更新。checkpoint、预处理、特征合同、导出逻辑或预期行为变化时，应该创建新模型版本、重新生成黄金向量、重新计算摘要并重新审批。新模型被旧黄金向量拒绝，是在防止版本混用，不是误杀。

**一句话总结：** SHA-256 是完整性证据，包外回执是授权绑定，黄金向量是数值兼容性证据；三者都不能单独证明临床有效性。

## 三、合成影像与融合

### 7. 合成眼底图是怎么生成的？

**推荐回答：**

它不是 GAN 或扩散模型，而是纯 Python 的确定性规则绘制：包括示意视野、视盘、黄斑、镜像血管树以及明显的 `SYNTHETIC OD/OS` 水印。生成过程不读取外部图像、不使用训练数据，也没有随机数。

它对真实疾病预测没有临床意义。它的意义是提供可复现的工程输入，用来验证：

- PNG 解码合同
- OD/OS 眼别绑定
- 像素摘要和来源校验
- 图像质量门
- 预处理与编码器接口
- 多模态融合和回退行为

所以不能说它证明了图像模型有效，只能说它证明了图像工程链路可测试、可复现。

### 8. “结构化锚定融合”具体怎么融合？

**推荐回答：**

当前不是把 9 维结构化特征和图像 embedding 拼接后训练一个联合模型，而是先由结构化模型产生逐眼锚点分数，再让图像分支对 logit 做有界修正：

```text
z_struct = logit(p_struct)
delta_eye = 0.35 * tanh(w_eye^T * image_embedding)
p_fused = sigmoid(z_struct + delta_eye)
```

图像编码器输出五个确定性统计量：

- 平均亮度
- 对比度
- 边缘能量
- 中心与周边差异
- 左右非对称度

因此，两个模态是在逐眼的 log-odds 层对齐，而不是通过真实数据学习跨模态语义。图像修正的绝对值被限制在 `0.35`，结构化结果始终是锚点。

这是一种融合接口与安全边界演示，不是经过临床训练的多模态模型。

### 9. “逐眼精确回退”何时触发？会调整不确定性吗？

**推荐回答：**

逐眼回退原因包括：

- `image_missing`
- `image_quality_rejected`
- `image_encoder_unavailable`
- `image_encoder_contract_error`

某一眼回退时，该眼的最终分数与结构化锚点使用完全相同的浮点值，`logit_adjustment=0`；另一眼仍然可以继续使用影像分支。

眼别冲突、像素摘要不匹配、重复图像或来源伪造不属于普通质量问题，会整单 fail-closed。编码器在本次请求中出现合同错误时，受影响眼回退；完成当前请求后，影像组件会锁定为 `not_ready`，避免未来请求继续使用异常编码器。

目前没有额外的置信区间，也没有 epistemic 或 aleatoric uncertainty 估计。系统只通过 `mode`、`reason_code`、锚点分数和调整量说明使用了哪条路径，这属于运行状态，不是统计不确定性。

真实系统应该分别校准结构化路径、融合路径和回退路径，并考虑置信区间、选择性预测或直接拒绝输出。

## 四、测试与工程质量

### 10. 145 项测试怎么分布？有没有失败路径测试？

**推荐回答：**

项目没有用 pytest marker 正式划分单元测试和集成测试，而且 145 是参数化后的 pytest item 数，不是 145 个独立测试函数。

按边界粗略分类：

- 约 84 项底层单元与合同测试：特征、领域模型、模型配置、模型合同、影像、融合、遥测和基准工具。
- 约 61 项 API、CLI、研究 adapter、公开工件策略和安全边界测试。

失败路径是测试重点，包括：

- 损坏的 checkpoint 哈希
- state dict 缺失或多余 key
- 错误 shape、dtype、NaN/Inf
- 过期、撤销或不匹配的审批回执
- 额外文件、超限文件和符号链接
- 黄金输出不匹配
- 模型特征顺序或归一化配置错误
- PNG CRC、chunk、尺寸和解压限制
- 图像眼别、摘要、质量与编码器合同错误

默认无 PyTorch 环境为 `140 passed, 5 skipped`，安装 CPU PyTorch 的完整 CI 为 `145 passed`。

### 11. Windows、多 Python 版本和 wheel 隔离安装遇到过哪些问题？

**推荐回答：**

比较有代表性的跨平台问题有：

1. `datetime.UTC` 只适用于 Python 3.11 及以上，为支持 Python 3.10 改为 `timezone.utc`。
2. `websockets 17` 要求 Python 3.11 及以上，最终锁定兼容 Python 3.10 的 `16.1.1`。
3. Windows 与 Linux 的数学库会产生最后几位浮点差异。即使随机种子相同，模型 JSON 仍可能字节不同。最终只在工件发布边界规范化为 12 位有效数字，不在训练循环里逐步舍入。
4. Windows 的 CRLF 与 Linux 的 LF 会影响工件摘要，因此固定 UTF-8、LF 和末尾换行。
5. 曾发现源码已经更新，但 `dist` 中仍是旧 wheel，因此增加了干净重建、wheel 内容比较和隔离安装 smoke test。

CI 不是所有平台和 Python 版本的完整笛卡尔积：Ubuntu 覆盖 Python 3.10 到 3.12，Windows 主要验证 Python 3.12 下的工件重生成，wheel 隔离安装在 Ubuntu 3.12 完成。

### 12. P95 延迟 55.3 ms、并发和异步情况如何？

**推荐回答：**

`55.291 ms` 是 Windows 11、Python 3.12 下，双眼合成影像场景经过预热后执行 300 次顺序迭代得到的 P95。

计时包含质量检查、32 x 32 预处理、统计编码和融合，但不包含：

- 图像文件读取
- HTTP 和网络
- 容器与反向代理
- 并发负载

而且这条多模态路径目前只在离线 CLI 中运行，没有接入 FastAPI。

当前没有并发压测，所以不能把这个数字解释成生产 SLA。公开 `/predict` 是同步 `def`，FastAPI 会通过线程池处理同步路由；项目没有自行实现异步推理、批处理或并发调优。CPU 密集计算也不会因为简单改成 `async def` 就自动变快。

真正开放服务前，我会测试并发 1、8、32 下的 P50、P95、P99、吞吐、错误率、CPU、内存和队列等待，再决定使用多 worker、独立推理进程、向量化或批处理。

## 五、项目边界与判断力

### 13. 没有真实患者数据，怎么验证真实分布？

**推荐回答：**

当前不能验证真实分布上的有效性。我验证的是工程逻辑，而不是临床结论。

合成数据可以证明特征顺序、校验、加载、确定性、API 合同和回退都能工作，也能证明模型可以拟合我定义的合成规律；但它不能证明真实人群中的患病率、变量关系、校准、泛化或公平性。合成 AUC 不能当成临床性能。

合成数据与真实临床数据的主要差距包括：

- 真实患病率和标签噪声
- 非随机缺失与测量误差
- 干预、佩镜行为等混杂因素
- 医院、设备和操作者偏移
- 亚组差异与时间漂移
- 真实两眼相关结构
- 真实眼底病变和成像伪影

真正验证时，需要使用已授权、去标识化的真实队列，明确预测时点和标签定义，按参与者拆分，并进行时间外、院外验证；报告 AUC、Brier score、校准曲线、置信区间和亚组表现。即使结果良好，也应先做前瞻性 shadow evaluation，而不是直接影响患者决策。

### 14. 从工程演示到临床系统，最大的 gap 是什么？

**推荐回答：**

最大的 gap 不是再换一个复杂模型，而是：

> 有代表性的授权数据、可追溯的临床有效性证据，以及完整的治理责任链。

技术层面还需要：

- 明确 intended use、预测标签和时间范围
- 真实缺失值与数据质量规则
- 参与者级拆分、院外及前瞻性验证
- 校准、亚组偏倚和漂移监测
- 真实图像的 DICOM 元数据、眼别和设备归一化
- 认证、授权、限流、审计、加密和事件响应
- 不确定性、人工复核、拒绝预测和安全回滚

合规层面还需要数据使用依据、伦理和机构审批、隐私影响评估、临床治理，以及根据具体司法辖区判断是否进入医疗器械软件的质量和风险管理流程。工程师不能仅凭代码自行宣布“符合医疗法规”。

最准确的项目定位是：

> LongiEye 当前是一个强调模型门禁、可追溯性和安全降级的非临床工程原型；它证明了如何可靠地接入模型，但没有证明该模型可以用于真实医疗决策。

## 面试中绝对不要说

- “变化量特征已经证明比原始值更好。”
- “OD/OS 是完整的联合概率模型。”
- “缺失值已经由模型智能处理。”
- “真实研究模型已经接入线上 API。”
- “合成眼底图验证了真实临床图像效果。”
- “55.3 ms 是并发 API 或生产环境性能。”
- “145 项测试证明模型具有临床有效性。”
- “系统已经符合医疗法规。”

## 30 秒总结

LongiEye 不是一个已经通过临床验证的医疗模型，而是一个非临床 AI 工程原型。它用严格数据合同管理两次随访输入，用模型 manifest、包外审批、SHA-256 和黄金向量建立 fail-closed 接入门禁，并通过结构化锚定融合演示合成影像质量控制和逐眼精确回退。项目的价值在于模型工程、安全边界、可复现性和诚实的适用范围，而不是合成数据上的临床性能。
